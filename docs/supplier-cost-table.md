# 项目供应商成本表说明

## 这张表解决什么问题

`项目供应商成本表` 用来按项目查看供应商成本闭环：

- 每个项目用了哪些供应商。
- 每个供应商对应哪些 PO。
- PO 成本金额是多少。
- 这个 PO 有没有付款申请。
- 这个 PO 是否已经实际付款。
- 付款申请是否已经收票。
- 付款申请或 PO 是否存在匹配异常。

这张表不是人工录入表。它由本地同步脚本生成和维护，日常查看、筛选、分组即可。

## 数据来源

| 来源表 | 读取内容 | 作用 |
| --- | --- | --- |
| `源_PO申请` | PO 申请编号、项目编号、项目名称、供应商、服务内容、PO 成本金额、PO 对客报价金额、PO 利润、审批状态 | 作为每条供应商成本记录的主来源。原则上每条 PO 生成一行。 |
| `源_付款申请` | 付款申请编号、关联 PO、付款申请金额、预计付款日期、发票情况、项目编号、供应商 | 汇总到对应 PO，用于判断有没有付款申请、有没有收票。 |
| `供应商付款` | 关联 PO、实际付款金额、实际付款日期 | 作为真实付款口径。付款申请不等于实际付款，只有这里的实际付款金额才算真实已付。 |
| `项目总览表` | 项目编号、项目记录 | 用来把供应商成本关联回项目。 |

脚本不会写入任何 `源_` 表，也不会写入 `（旧项目）开票计划补录表`。

## 一行代表什么

正常情况下，一行代表一条 PO。

唯一键规则：

```text
成本唯一键 = PO|源_PO申请.SourceID
```

如果 `源_PO申请.SourceID` 缺失，则用 PO 记录 ID 兜底。

如果 `源_付款申请` 里有付款记录，但找不到对应 PO，会额外生成一条异常行：

```text
成本唯一键 = 付款未匹配PO|源_付款申请.SourceID
```

这样做的目的不是把异常当作正常成本，而是让无法闭环的数据能被看见并处理。

## 核心字段规则

| 字段 | 规则 |
| --- | --- |
| `成本记录标题` | 脚本生成，通常为“项目编号-供应商-PO申请编号”。 |
| `成本唯一键` | 脚本幂等同步用，不建议人工修改。 |
| `关联项目` | 按项目编号匹配 `项目总览表`。匹配不到时为空。 |
| `关联PO` | 关联到 `源_PO申请` 的原始记录。 |
| `关联付款申请` | 关联到当前 PO 下的 `源_付款申请`，一条 PO 可关联多条付款申请。 |
| `项目编号` | 优先来自 `源_PO申请.项目编号1`；付款未匹配 PO 的异常行来自 `源_付款申请.项目编号1`。 |
| `项目名称` | 优先来自 `源_PO申请.项目名称1`。 |
| `供应商` | 优先来自 `源_PO申请.供应商名称1`。 |
| `服务内容` | 来自 `源_PO申请.服务内容1`。 |
| `PO申请编号` | 来自 `源_PO申请.申请编号`。 |
| `PO申请状态` | 来自 `源_PO申请.申请状态`。 |
| `PO成本金额` | 来自 `源_PO申请.金额1`，这是供应商项目成本口径。 |
| `PO对客报价金额` | 来自 `源_PO申请.该po对客报价金额`。 |
| `PO利润` | 来自 `源_PO申请.利润`。 |
| `付款申请金额合计` | 汇总当前 PO 下所有 `源_付款申请.金额1`。这是申请金额，不代表实际付款。 |
| `实际付款金额合计` | 汇总 `供应商付款.实际付款金额`。这是实际付款口径。 |
| `未付款金额` | `PO成本金额 - 实际付款金额合计`，小于 0 时按 0 显示。 |
| `付款申请编号汇总` | 汇总当前 PO 下所有付款申请编号，多个用顿号分隔。 |
| `最近付款申请日期` | 当前 PO 下最新一条付款申请的发起时间。 |
| `最近预计付款日期` | 当前 PO 下最新一条付款申请的付款日期。 |
| `最近实际付款日期` | `供应商付款` 中当前 PO 最近一次实际付款日期。 |
| `最后同步时间` | 只有本次同步实际改动记录时写入；如果本次数据没变化，会清空，避免误判为今天更新过。 |

## 付款状态规则

| 付款状态 | 判断规则 |
| --- | --- |
| `PO未通过` | PO 申请状态不是 `已通过`。 |
| `未申请付款` | PO 已通过，但没有付款申请，也没有实际付款。 |
| `已申请待付款` | 有付款申请金额，但实际付款金额为 0。 |
| `部分付款` | 实际付款金额大于 0，但小于 PO 成本金额。 |
| `已付款` | 实际付款金额等于 PO 成本金额。 |
| `超额付款` | 实际付款金额大于 PO 成本金额。 |

这里需要特别注意：`源_付款申请` 只能说明有人提交了付款申请，不代表财务已经付款。实际付款以 `供应商付款.实际付款金额` 为准。

## 发票状态规则

发票状态来自 `源_付款申请.发票情况`。

| 发票状态 | 判断规则 |
| --- | --- |
| `未申请付款` | 当前 PO 没有关联付款申请。 |
| `已收票` | 当前 PO 下所有付款申请的发票情况都是 `收到`。 |
| `部分收票` | 当前 PO 下有的付款申请是 `收到`，有的是 `未收到`。 |
| `未收票` | 当前 PO 下所有付款申请的发票情况都是 `未收到`。 |
| `待确认` | 发票情况不是以上标准值，脚本无法可靠判断。 |

## 数据匹配状态规则

| 数据匹配状态 | 含义 |
| --- | --- |
| `已匹配项目和付款` | PO 能匹配到项目总览表，并且有关联付款申请。 |
| `已匹配项目未匹配付款` | PO 能匹配到项目总览表，但还没有付款申请。 |
| `项目未匹配` | PO 里没有项目编号，或项目编号在 `项目总览表` 中找不到。 |
| `付款未匹配PO` | 付款申请里的 `关联po` 找不到对应的 `源_PO申请`。 |

## 异常原因

`异常原因` 是脚本自动写入的处理提示，目前主要包括：

- `项目编号未匹配项目总览表`
- `付款申请未匹配到源_PO申请`
- `实际付款超过PO成本`
- `PO申请未通过`

建议日常重点查看这些异常视图：

- `付款未匹配PO`
- `超额付款`
- `未付款`
- `未收票`

## 不能做什么

- 不要在这张表里手工新增 PO 成本记录。下次同步不会把手工记录当作正式源数据。
- 不要手工修改 `成本唯一键`、`关联PO`、`关联付款申请`。
- 不要把 `付款申请金额合计` 当作实际已付款。
- 不要直接写 `源_PO申请` 或 `源_付款申请`。
- 不要把 `项目未匹配` 当成正常项目成本，需要先补齐或修正项目编号。

## 当前已知边界

- 如果 `源_付款申请.关联po` 里没有可识别的 PO 申请编号，脚本只能标记为 `付款未匹配PO`。
- 如果 `供应商付款` 没有维护实际付款金额，即使付款申请已通过，也只能显示为 `已申请待付款`，不能显示为 `已付款`。
- 如果 PO 的项目编号为空，或项目总览表没有这个项目编号，会显示为 `项目未匹配`。
- 这张表只做供应商成本和付款收票闭环，不替代 `项目总览表` 的项目分类、老板驾驶舱、开票收款统计。
